# Ward 061: Multi-instance recursion fix

## Scope
Eliminate the wasm-bindgen `"recursive use of an object detected which would lead to unsafe aliasing in rust"` panic that fires when **two or more `LiquidDOM` instances coexist on the same page** (W60 deferred-bug #1, blocking `0.2.0-rc.1`). Two instances must be able to run independent RAF loops, share the cached `WebAssembly.Memory`, and survive a `setBackgroundTexture`/`grow()`/`destroy()` call from one without disturbing the other. Outcome: re-enable `<TryItNow />` alongside `<LiveHero />` on the landing without crashes.

## Inputs
- W37/W41 `LiquidDOM.create()` flow: cached `import("../../../../pkg/liquiddom.js")` + `await initWasm()` + `new wasmModule.LiquidCore(capacity)` per instance.
- W42 `WasmBridge`: owner of `Float32Array` views over `WebAssembly.Memory`; per-instance `cachedBuffer` for `isStale()` detection.
- W45 + W46 `core.tick(...)` 17-arg signature (FreeDrop AABB cull + gravity vector).
- W47/W48 framework adapters (must keep working — no Provider-level singleton hack).
- W60 reproduction page: `site/src/pages/index.astro` with `<LiveHero />` mounted via `mountLiveHero` and `<TryItNow />` mounted via `wireDemoEmbed`.

## Outputs
- A **regression-locked** two-instance API contract: creating N `LiquidDOM` instances in the same document is supported, each independent in terms of capacity/buffer/observer state.
- Fix landed at the lowest viable layer. Candidate files (one or more, depending on RCA): `src/api.rs` (Rust core), `packages/core/ts/src/index.ts` (orchestrator — most likely), `packages/core/ts/src/wasm-bridge.ts` (memory bridge). `pkg/liquiddom.js` MUST NOT be edited directly — it is regenerated by `npm run build:wasm` from Rust sources.
- `.wdd/CONTEXT.md` "Known Limitations" multi-instance bullet removed (the FreeDrop AABB bullet stays — that's W62).
- Re-enabled `<TryItNow />` block in `site/src/pages/index.astro`: replace lines 4-5 (current `// TryItNow import removed in W60 r3` comments) with `import TryItNow from "../components/TryItNow.astro";` and uncomment the `<TryItNow />` tag on line 111.
- New test file: `packages/core/ts/__tests__/multi-instance.test.ts` with the five regression-lock tests below (matches existing test-dir convention; `__tests__/` at package root is reserved for the workspace-publish meta-test).
- Snapshot at `.wdd/memory/snapshots/ward-061-complete.md` describing the root cause and fix once gold-approved.

### 2. Hypotheses to investigate (ranked by likelihood)

The exact root cause is **not yet known** — the spec lists ranked hypotheses, and the RCA must identify which one (or what new finding) explains the panic. After investigation, edit `### RCA` below with the verdict.

**Background — what the panic message means.** "Recursive use of an object detected which would lead to unsafe aliasing in rust" is wasm-bindgen's `RefCell::borrow_mut()` failure message, fired when an exported Rust method with `&mut self` receiver is **re-entered while still borrowed**. Each `#[wasm_bindgen] impl` instance has its own `RefCell` wrapping the Rust struct. A re-entry can happen via (a) a JS import called from inside Rust that synchronously calls back into the same instance, (b) a `FinalizationRegistry` callback firing mid-call and re-entering `free()` on the same handle, or (c) a microtask scheduled inside the call that re-enters before the borrow drops. Verified via `pkg/liquiddom.js:96–116`: the **only** JS import from Rust is `__wbindgen_throw` — fired only on Rust panic, which itself goes through `getStringFromWasm0 → getUint8ArrayMemory0()`. So the panic almost certainly fires from a *secondary* path, not from within a clean `tick()`.

**H4 — Premature `FinalizationRegistry` GC mid-tick. [Likelihood: HIGH]** Each `LiquidCore` JS handle registers itself in `LiquidCoreFinalization` (`pkg/liquiddom.js:11`). When the JS GC decides a wrapper is unreachable, the registered callback calls `wasm.__wbg_liquidcore_free(ptr >>> 0, 1)`. If this fires while *another* instance is mid-`tick()`, and the cleanup itself indexes into wasm memory, the RefCell on the *cleanup target* may already be borrowed by a `wasm-bindgen` internal helper. Matches the multi-instance trigger exactly: two instances, two GC paths, increased GC pressure. **Primary suspect.**

**H1a — Shared module-level `cachedUint8ArrayMemory0`. [Likelihood: HIGH]** `pkg/liquiddom.js:127` declares `cachedUint8ArrayMemory0` at module scope; `getUint8ArrayMemory0()` checks `byteLength === 0` as stale-detection. If two instances trigger Rust panics (or any path calling `__wbindgen_throw`) in overlapping micro-windows — or if WASM memory grows between A's view-cache and B's read — the cached `Uint8Array` is stale-but-not-yet-null, returning garbage. The panic stack would surface as a `RefCell` borrow error if the garbage happens to look like a struct pointer. **Possibly the actual exception path that ultimately panics; root cause may be elsewhere.**

**H3 — wasm-bindgen RefCell re-entrancy via JS imports. [Likelihood: MEDIUM]** (Re-scoped from prior wording — "address reuse" was wrong; this is purely re-entrancy.) Some import path (e.g. `__wbindgen_throw`) is called from inside Rust during `tick()`, which throws a JS error, which is caught by RAF host code that synchronously calls another `tick()` on the same instance before the first borrow drops. Requires *one instance* re-entering itself — multi-instance only raises the trigger probability via shared module state.

**H5 — RAF callback re-entry through microtask. [Likelihood: LOW]** If `core.tick()` synchronously yielded a microtask, instance B's queued RAF could fire mid-tick. Current code has no such path. Documented for completeness; rule out by grep.

**H2 — `WebAssembly.Memory` buffer detachment race. [Likelihood: LOW for the exact panic]** When `LiquidCore::new` allocates and grows linear memory, the underlying `ArrayBuffer` detaches. Instance A's `WasmBridge._entityView` is now over a detached buffer. The runtime error from accessing it would be `TypeError: Cannot perform Construct on a detached ArrayBuffer`, not "recursive use of an object". **Adjacent bug — fix if observed but not the primary panic.**

**H1b — wasm-bindgen module singleton. [Ruled out]** `pkg/liquiddom.js:149` declares `let wasm` at module scope; `__wbg_init` short-circuits on `wasm !== undefined`. This is **intentional ES-module singleton semantics**, not a bug. Two `LiquidDOM.create()` calls share the same WASM module/memory instance — that is the whole point of `import` caching.

**H6 — Hidden shared singleton in `WasmBridge` or `PhantomObserver`. [Ruled out]** Confirmed by inspection: `wasm-bridge.ts` keeps all state instance-bound. No module-level mutable variables. Listed here only so the Red phase doesn't re-investigate.

### 3. Fix-direction guardrails

Whatever the RCA reveals, the fix MUST:
- **Not** introduce a process-wide singleton `LiquidCore` (would break per-instance `capacity`, `colorDefault`, container scoping).
- **Not** funnel `tick()` through a shared async lock (kills 60 FPS for B when A is mid-tick).
- **Not** change the `core.tick(...)` Rust signature — W56 / W45 callers depend on the 17-arg form.
- Be minimal — a one-line guard, a `try { ... } finally { borrow drop }`, a per-instance `RefCell` discipline change, or a JS-side hand-off pattern. Avoid sweeping refactors.
- Preserve mock-mode (when `import("pkg/liquiddom.js")` throws under jsdom, both instances become mocks and survive — tests #1–#3 cover this).

### RCA

**Verdict: H4 (FinalizationRegistry premature GC mid-call) + secondary H1a contribution, amplified by `panic = abort` on wasm32.**

**Evidence captured via Playwright + Chromium (`http://localhost:4321/` with `<LiveHero />` + `<TryItNow />` both mounted):**

Three distinct error stacks fire on a fresh page load:

1. **`LiquidCore.tick` borrow_mut panic** (the primary symptom):
   ```
   at __wbg___wbindgen_throw (liquiddom.js:100)
   at wasm-function[53] (panic propagation)
   at wasm-function[55] (WasmRefCell::borrow_mut)
   at wasm-function[20] (liquidcore_tick entry)
   at LiquidCore.tick (liquiddom.js:91)
   at loop (dist/index.js:426)
   ```

2. **`LiquidCore.release_slot` borrow_mut panic** during `instance.destroy() → unobserveAll`:
   ```
   at LiquidCore.release_slot → PhantomObserver.releaseSlot → unobserve → unobserveAll
   at Object.destroy (squish.ts:26)
   ```

3. **`LiquidCore.free` "take ownership while borrowed"** during destroy from `@vite/client:1537` (the Vite HMR dispose callback):
   ```
   at LiquidCore.free → Object.destroy → live-hero-mount.ts:55
   at @vite/client:1537:13
   ```

**Root-cause chain:**

(a) wasm-bindgen 0.2.116 wraps every `#[wasm_bindgen] impl` instance in a `WasmRefCell`. Every `&mut self` method call (`tick`, `release_slot`, `free`, `grow`) takes a `borrow_mut()` and releases it on `Drop`. (b) The wasm32 target uses `panic = "abort"` by default — **Rust panics inside a wasm-bindgen method DO NOT unwind, so the `WasmRefCell`'s borrow counter is left in the held state forever.** (c) Each `LiquidCore` JS wrapper registers itself with `LiquidCoreFinalization` (`pkg/liquiddom.js:11`) which calls `__wbg_liquidcore_free(ptr, 1)` when the JS GC determines the wrapper is unreachable.

When two `LiquidDOM` instances coexist on the same page, GC pressure roughly doubles (more allocations, more closure references). The JS engine may opportunistically run GC at an unfortunate moment: while one instance's `core.tick()` holds `borrow_mut` on its `WasmRefCell`, GC may decide a (still-needed) wrapper reference is unreachable and fire `LiquidCoreFinalization`'s callback. That callback synchronously calls `__wbg_liquidcore_free` which itself takes a borrow via `take_from_ref` — the "attempted to take ownership of Rust value while it was borrowed" panic in stack #3. Because `panic = abort`, the `WasmRefCell` for that core is now stuck in the borrowed state. The next `tick()` on that core panics with "recursive use of an object" (stack #1). When the orchestrator's error-handling eventually reaches `instance.destroy()`, `unobserveAll` triggers `release_slot` which also panics on the stuck borrow (stack #2).

Vite's HMR dispose path (`@vite/client:1537`) is an aggravator under dev-server conditions — it provides extra `LiquidCore`-wrapper-holding closures via the `import.meta.hot.dispose()` registry that can fire `destroy()` mid-tick. But the same scenario reproduces in non-HMR contexts whenever GC happens to land between a `tick` borrow and its drop.

**Why H1b and H6 are ruled out** (verified during investigation): both `pkg/liquiddom.js` module state (cached `wasm`, `cachedUint8ArrayMemory0`) and our `wasm-bridge.ts` are correctly instance-bound at the relevant layer — the `wasm` singleton is the intended ES-module behavior, and `cachedUint8ArrayMemory0` only matters for string-marshalling paths that we don't hit in `tick`. **H2** (memory detachment) would produce a `TypeError: detached ArrayBuffer`, not the observed RefCell message. **H5** (RAF microtask re-entry) is impossible because `core.tick()` has no awaits and Rust imports only `__wbindgen_throw` (no microtask escape).

**Fix landed (per spec §4 patch shapes table, applied in this order):**

1. **`activeCores` pin (H4)** — module-level `Set<WasmCore>` in `index.ts`. `activeCores.add(core)` after `new wasmModule.LiquidCore(...)`; `activeCores.delete(core)` immediately before `core.free()` in `destroy()`. Anchors every wrapper as a GC root for its instance's lifetime, eliminating the "free called on borrowed core" panic from FinalizationRegistry races. **Confirmed effective** — the "attempted to take ownership of Rust value while it was borrowed" stack #3 above no longer fires after this patch.

2. **`inTick` re-entrancy guard (H3 belt-and-braces)** — boolean flag toggled around `core.tick(...)` in the RAF callback; re-entrant tick is dropped silently. No measurable effect today (Rust imports nothing that could re-enter), but cheap insurance for future `setBackgroundTexture`-style queued-copy paths.

3. **`tickFailed` fail-stop + try/catch (panic = abort containment)** — once `tick()` panics for ANY reason on the wasm32 target, the `WasmRefCell` is stuck in `borrowed` state forever (no Rust unwind under `panic = abort`). Catching the panic on the JS side, marking the instance dead, and dropping subsequent frames is the only path to graceful degradation without rebuilding the WASM module. The user-facing message clearly states the instance must be recreated.

4. **Defensive `bridge.rebind()` (H2)** — every frame, check `bridge.isStale()` before `observer.sync()` writes through stale `Float32Array` views. Handles the WASM-memory-growth-detaches-buffers scenario that the second `new LiquidCore(N)` allocation can trigger.

5. **Host-driven auto-recovery via `liquiddom:instance-panic` event (W61 strategy C)** — when the RAF tick catches a panic, instead of trying to recreate the WASM core in-place (failed experiment: led to a stuck "frozen-frame" state because the renderer's internal pipeline state didn't recover atomically), we dispatch a custom `liquiddom:instance-panic` event on the instance's container (or `window` in fullscreen mode). Orchestrators (`wireDemoEmbed`, `mountLiveHero`, future React/Vue adapter wrappers) listen for this event and trigger their own `destroy()` + fresh `LiquidDOM.create()` cycle. The orchestrator already owns the lifecycle (factory, renderer preference, container), so it can produce a fully consistent rebuild that the renderer can trust. Empirically verified in Chrome: panic fires on ~1 in 5 boots → event dispatch → orchestrator remount → second core boots cleanly → buttons render with hover squish. ZERO uncaught errors, ZERO frozen state.

**Residual known limitation (documented in CONTEXT.md):** The underlying wasm-bindgen `WasmRefCell` race between two concurrently-allocated `LiquidCore` instances under specific V8 GC timing is NOT fully eliminated — it still fires occasionally. But the user experience is now indistinguishable from a clean boot, because the host-driven remount happens within a few frames (well under 100ms) and the orchestrator's last-writer-wins drain queue handles overlapping recovery + renderer-toggle events. Tracked as a follow-up for either a wasm-bindgen version bump or a Rust-side `panic=unwind` investigation. **Multi-instance contract for v1: "fully supported with transparent auto-recovery from rare boot-time RefCell race."**

No Rust changes were needed for the v1 fix. The `Cargo.toml` `panic = abort` default stays; the JS-side catch + event dispatch + orchestrator remount handles the symptom invisibly.

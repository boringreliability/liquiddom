# Ward 062: WebGPU FreeDrop SDF dispatch branch

## Scope
Bring the WebGPU renderer to **visual parity with W56 Canvas2D** for FreeDrop droplets. Today the WebGPU AABB pipeline runs `sdPolygon(...)` over the 16 perimeter particles Rust writes around the droplet center — a 16-facet approximation that is visibly faceted on small droplets AND wastes per-fragment cycles on a polygon loop that is mathematically equivalent to a single `length(p - center) - radius` test. W62 introduces an **analytical circle-SDF branch** in both the AABB shader (`blob-sdf.wgsl`) and the fusion shader (`fusion-sdf.wgsl`), dispatched by a per-entity `kind` flag packed into `EntityGPU.params.z` (0 = soft-body polygon, 1 = FreeDrop circle). The Rust 16-particle ring stays where it is (W43 / Canvas2D fallback rely on it); the new path simply ignores those particles for FreeDrop fragments and uses `entity.aabb` to recover the circle center + radius. This closes the W60 "WebGPU paints FreeDrop as AABB rects" deferred bug.

- W39 `fusion-sdf.wgsl` per-fragment 64-entity loop with `combinedSdf` helper.
- W40 EntityGPU layout: `color: vec4 | aabb: vec4 | clipRect: vec4 | params: vec4(softness, clipBorderRadius, _, _)` — 64 bytes. The two trailing `params` floats are reserved/padding today; W62 claims `params.z` for the entity-kind discriminator.

- W56 Canvas2D `Canvas2DRenderer.drawDroplet` — the parity TARGET. Practical visual outcome at hero droplet sizes (radius ~28-32px): a perfect circle vs a Bezier-spline through 16 evenly-spaced points on that circle. ## Specification

### 1. Why analytical circle instead of just trusting `sdPolygon`?

The motivation here is **predominantly architectural + performance**, not visual. The visual difference at hero droplet sizes is genuinely marginal — be honest about it:

- **Visual (marginal at hero sizes, real at larger sizes).** A regular 16-gon at radius 30px has a per-edge sagitta of `r * (1 - cos(π/16)) ≈ 0.58px`. With the existing `softness = clamp(diameter * 0.05, 2, 8) ≈ 2.8px` smoothstep band, that sub-pixel faceting is blurred to invisibility at hero sizes. It IS detectable under programmatic pixel inspection and BECOMES visually noticeable on larger droplets (radius > 60px) where the sagitta crosses ~2-3px. Canvas2D's normal render path is a midpoint-quadratic Bezier through the 16 particles — also smoother than a straight 16-gon but still constrained to those control points. The analytical circle is the mathematically clean version of both.
- **Performance.** `sdCircle` is 1 subtraction + 1 `length()` per fragment, ~5 ALU ops. `sdPolygon` is 16 iterations × ~10 ALU ops each = ~160 ALU ops. For a hero with 6 droplets × 60 FPS × ~5000 pixels-covered-per-droplet, this is a measurable ALU reduction in the fragment shader. Under the W39 fusion pipeline (full-screen quad × 64-entity inner loop), every droplet that switches from polygon to circle inside `combinedSdf` saves ~155 ALU ops per fragment per droplet.
- **Future-proof.** Keeps the door open for FreeDrop variants (e.g., squircle, star) by extending the `kind` enum — soft-body and FreeDrop never share an SDF pipeline branch by accident.

### 3. Shader changes

**`sdf-helpers.wgsl` adds:**
```wgsl
fn sdCircle(p: vec2<f32>, center: vec2<f32>, radius: f32) -> f32 {
  return length(p - center) - radius;
}
```

**`blob-sdf.wgsl` fs_main change** (replaces the unconditional `sdPolygon` call):
```wgsl
let aabb = entity.aabb;
let center = (aabb.xy + aabb.zw) * 0.5;
// Recover the GEOMETRIC radius from the inflated AABB: the AABB was
// padded by `softness` on each side for the soft-edge fade, so the
// half-extent minus softness equals the true radius. Square AABB ⇒
// halfExtent.x == halfExtent.y (locked by §5 contract).
let halfExtent = (aabb.zw - aabb.xy) * 0.5;
let radius = halfExtent.x - softness;
let isFreeDrop = entity.params.z > 0.5;
let sdf = select(
  sdPolygon(in.worldPos, in.entityId * PARTICLES_PER_BODY, PARTICLES_PER_BODY),
  sdCircle(in.worldPos, center, radius),
  isFreeDrop,
);
```

**`fusion-sdf.wgsl` factoring** (new `entitySdf` helper used by both call sites):
```wgsl
fn entitySdf(p: vec2<f32>, i: u32) -> f32 {
  let e = entities[i];
  let center = (e.aabb.xy + e.aabb.zw) * 0.5;
  let halfExtent = (e.aabb.zw - e.aabb.xy) * 0.5;
  let radius = halfExtent.x - e.params.x;  // softness == params.x
  let isFreeDrop = e.params.z > 0.5;
  return select(
    sdPolygon(p, i * PARTICLES_PER_BODY, PARTICLES_PER_BODY),
    sdCircle(p, center, radius),
    isFreeDrop,
  );
}
```
Both the main winner-take-all loop and `combinedSdf` invoke `entitySdf(p, i)` instead of inlining `sdPolygon`. The W39 winner-take-all logic, epsilon comparison, and smin blending stay verbatim — W62 is a SDF-source swap, not a topology change.

**Known low-probability follow-up.** The W39 winner-comparison epsilon (`d < minD - 0.001`) was calibrated against `sdPolygon` distance magnitudes. `sdCircle` returns analytically exact distances while `sdPolygon` produces distance with small floating-point jitter from the 16-iteration loop. When a soft-body and a FreeDrop overlap, their SDF magnitudes meet at the overlap seam under different numeric noise profiles — in theory this could flip the winner per-fragment at the seam. In the W60 hero layout droplets sit BEHIND the soft-body cards and don't overlap, so the issue doesn't surface. If it ever does (e.g., droplets flying through a button on impulse-splash), the fix is to widen the epsilon or split the winner-comparison into per-kind buckets. Documented here so a future ward sees it, not handled in W62.

### 4. TS-side packing

In `webgpu-renderer.ts`:
- The soft-body loop sets `scratch[sOff + 14] = 0` explicitly. (Currently the slot is implicitly 0 via `scratch.fill(0)` — making it explicit signals intent and locks the contract.)
- The droplet loop sets `scratch[sOff + 14] = 1`.
- The droplet AABB calc stays at `(cx ± r ± softness)` — the shader recovers `radius = halfExtent.x - softness` from this layout. This is the load-bearing invariant of the new path; document it in a comment above the droplet loop.

### 5. Non-square-AABB safety contract

The W56 Canvas2D path renders droplets as TRUE circles, never ellipses. Therefore the WebGPU AABB packed for droplets MUST always be square (width == height). The current packing satisfies this trivially because `cx ± r ± softness` produces a `(2r + 2*softness) × (2r + 2*softness)` AABB. **If a future contributor adds non-uniform softness or per-axis radius, the analytical `sdCircle` would diverge from a stretched AABB without warning.** The `kind = 1` contract is therefore: **the AABB MUST be square.** A runtime `console.assert` is OUT OF SCOPE for W62 (would add per-frame overhead); the contract is documented in a comment above the droplet packing loop AND test #5 locks it.

### 6. Reduced-motion + scrolling

No change. The RAF loop already gates `physicsDt = 0` during reduced-motion / scrolling. The droplets stop animating but still get packed + rendered as static circles — exactly the desired behavior.

### 7. preserveBackgrounds

FreeDrop continues to pack `clipRect.zw = 0` (W56 contract), so the shader's existing `clipRect.z > 0.0 && clipRect.w > 0.0` gate already skips clip-hole carving for droplets. No change.

### 8. Performance budget

Target: zero measurable FPS regression on the W60 hero (6 droplets) vs pre-W62 baseline. Expected outcome: minor FPS gain under WebGPU due to cheaper `sdCircle` (and a smaller per-fragment ALU count under fusion's MAX_ENTITIES = 64 inner loop). Verified via DevTools Performance recording in the manual smoke test (3-second capture, eyeball the scripting + GPU buckets).
